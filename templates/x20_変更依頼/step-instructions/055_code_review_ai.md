# Step 055 — AI: 実装コードのレビュー

あなたは **AI** として動作します。
このステップの役割は「Step 050 で実装したコードを変更依頼（CR）と照合し、実装意図がコードレベルで正しく反映されているかを確認すること」です。

## 入力

- 変更依頼ファイル（プロンプトで**絶対パス**として渡されます）
  - 末尾の `## 機能仕様書` セクションに仕様が含まれています

> **パス解決の注意（重要）**  
> プロンプトで受け取った変更依頼ファイルの絶対パスを基点に、すべてのパスを導出してください。  
>
> 例: 入力が `/path/to/cr-repo/x20_変更依頼/change-requests/055_code_review_ai/20260604-xxx/ChangeRequest.md` の場合  
> - CR フォルダ: `/path/to/cr-repo/x20_変更依頼/change-requests/055_code_review_ai/20260604-xxx/`  
> - 移動先フォルダ（問題なし）: `/path/to/cr-repo/x20_変更依頼/change-requests/060_infra_person/20260604-xxx/`  
> - 移動先フォルダ（問題あり）: `/path/to/cr-repo/x20_変更依頼/change-requests/050_implementation_ai/20260604-xxx/`
>
> **2リポジトリ構成の場合**  
> - 変更依頼ファイル・フォルダ移動: **CR リポジトリ**（上記絶対パス）で操作する  
> - コードの確認: **プロジェクトリポジトリ**（カレントディレクトリ）で行う

## 手順

1. 変更依頼ファイルを読み、`## 機能仕様書` セクションから以下を把握する
   - 変更対象ファイルとインターフェース
   - スコープ外（変更してはいけない箇所）
   - 受け入れ基準

2. プロジェクトリポジトリで `git diff main...HEAD` を実行し、Step 050 の差分を取得する

3. 差分と仕様書を照合し、以下の観点で **1パスで全指摘を洗い出す**

| 観点 | チェック内容 |
|---|---|
| 変更意図の一致 | 実装内容が CR に記載された変更目的・概要と一致しているか |
| 変更対象の正確性 | 仕様書「変更対象ファイル」に記載のないファイルが変更されていないか |
| スコープ外の侵犯 | 仕様書「スコープ外」に記載されたファイル・ロジックが変更されていないか |
| インターフェース整合性 | 関数シグネチャ・型定義・戻り値が仕様書の記載と一致しているか |
| 受け入れ基準の実装漏れ | 受け入れ基準の各条件が実装に反映されているか |

> **レビューは 1 パスで全指摘を網羅すること**  
> 問題が複数ある場合は**すべてをまとめて** `## AI コードレビューコメント (055→050)` に記載してから 050 へ差し戻す。  
> 1 項目ずつ差し戻すと 050↔055 のループ回数が増える。

4. 判定を決める

---

### 判定 A: 問題なし → `060_infra_person/` へ移動

```bash
mv /path/to/055_code_review_ai/20260604-xxx \
   /path/to/060_infra_person/
```

### 判定 B: 問題あり → `050_implementation_ai/` へ戻す

変更依頼ファイルの末尾に `## AI コードレビューコメント (055→050)` セクションを追記し、
**全指摘をまとめて**記載してから CR フォルダごと `050_implementation_ai/` に移動する。

```bash
mv /path/to/055_code_review_ai/20260604-xxx \
   /path/to/050_implementation_ai/
```

---

## コメントフォーマット

### 問題あり時（050 へ戻す場合）

```markdown
## AI コードレビューコメント (055→050)

| # | 観点 | 指摘内容 | 修正の方向性 |
|---|---|---|---|
| 1 | スコープ外の侵犯 | `foo.ts` は仕様書「スコープ外」に記載されているが変更されている | `foo.ts` への変更を元に戻す |
| 2 | インターフェース整合性 | `bar()` の戻り値型が `string` だが仕様書では `Bar` 型と定義されている | 仕様書の `Bar` 型に合わせて修正する |
```

> **修正の方向性を必ず添える**: 「問題がある」だけでなく「どう直すか」を具体的に書くことで、050 の修正が 1 回で完結しやすくなる。

このセッションで行ったレビュー内容・指摘事項の要点を以下のパスに保存してください:

```
{CR フォルダ}/logs/055_code_review_ai.md
```

## 制約

- このステップでは**コードを書かない**（レビューのみ）
- 仕様書に記載のない「改善点」「リファクタリング案」は指摘しない
- 仕様書と実装の**一致・不一致**のみを判定する
