# Step 100 — AI: 仕様書・ドキュメント更新

あなたは **AI** としてドキュメント更新を担当します。
このステップの役割は「実装内容に合わせたドキュメントの同期」です。

## 入力

- 変更依頼ファイル（プロンプトで**絶対パス**として渡されます）
  - 末尾の `## 機能仕様書` セクションに変更内容・スコープが含まれています

> **パス解決の注意（重要）**  
> プロンプトで受け取った変更依頼ファイルの絶対パスを基点に、すべてのパスを導出してください。  
>
> 例: 入力が `/path/to/project/x20_変更依頼/change-requests/100_docs_ai/20260604-xxx/change-request.md` の場合  
> - CR フォルダ: `/path/to/project/x20_変更依頼/change-requests/100_docs_ai/20260604-xxx/`  
> - 移動先フォルダ: `/path/to/project/x20_変更依頼/change-requests/110_pr_ai/20260604-xxx/`

## 手順

1. 変更依頼ファイルを読み、末尾の `## 機能仕様書` セクションから今回の変更内容・スコープを把握する
2. スコープ内のソースファイルを読み、変更された機能の「何を・なぜ」を把握する（実装詳細は後述の方針に従い仕様書に書かない）
3. 以下のドキュメントを実装内容に合わせて更新する

| 対象ドキュメント | 更新内容 |
|---|---|
| `README.md` | 機能追加・変更があれば概要・使い方を更新 |
| `AGENTS.md` | AI 向けのコマンド・規約に変更があれば更新 |
| `x30_仕様書/` | 実装内容に合わせて該当仕様書を更新（後述の**概要優先ルール**に従う） |

4. CR フォルダごと `110_pr_ai/` に**絶対パスで**移動する

   ```bash
   mv /path/to/100_docs_ai/20260604-xxx \
      /path/to/110_pr_ai/
   ```

5. 更新内容をフィーチャーブランチにコミットする

## コミットメッセージ規約

```
docs: ドキュメントを実装内容に同期

Refs: x20_変更依頼/change-requests/100_docs_ai/YYYYMMDD-xxxx/change-request.md
```

## 制約

- このステップでは**コードを変更しない**（ドキュメント更新のみ）
- `main` への直接コミット禁止
- 仕様書の「スコープ外」に記載されたファイルのドキュメントは変更しない

## 仕様書の記述方針（概要優先）

> **原則: 仕様書は「何を・なぜ」を伝える。「どのように」はコードを読めばわかるため省略する。**
>
> 目標は「新しいメンバーが 5 分で概要を把握できる 1 ページのドキュメント」。
> 詳細を知りたい読者はコードを参照する。

### 書くべきこと

| カテゴリ | 記述例 |
|---|---|
| 目的・背景 | 「このモジュールは〇〇のために存在する」 |
| アーキテクチャ概要 | 主要コンポーネントとその役割・関係性（箇条書き or 表） |
| データの流れ | 入力元 → 処理 → 出力先（型の列挙は不要） |
| 設計上の判断 | 「〇〇方式を採用した理由」「代替案を採用しなかった理由」 |
| 重要な制約・前提 | 「〇〇が必要」「△△の場合は動作しない」 |
| 関連ファイルへのリンク | 主要エントリポイントへの `[[ノート名]]` または相対パス |

### 書かないこと（コードを見ればわかるため不要）

- 関数・メソッドのシグネチャや処理フロー
- SQL 文・クエリの内容
- 変数名・クラス名の列挙
- 設定値の羅列（config ファイルを参照すればよい）
- ループ・条件分岐の詳細

### 記述前の自己チェック

仕様書に書こうとしている内容について、以下を自問してください:

- [ ] コードを読んでも即座にはわからない情報か？（すぐわかる → 省略）
- [ ] 新しいメンバーがシステム全体を理解するのに必要か？（不要 → 省略）
- [ ] 設計の「なぜ」を説明しているか？（「何を」だけなら要検討）

## AI 向け仕様書生成の手順

仕様書を新規作成または更新する際は、以下の手順で進めてください。

### ステップ 1: インプット収集

以下を順番に読み込む:

1. `change-request.md` の `## 機能仕様書` セクション（変更のスコープ・意図）
2. スコープ内のソースファイル（変更内容の把握）
3. 既存の仕様書（更新の場合 — 変更箇所のみ特定する）

### ステップ 2: 書くことを決める

コードを読んだ後、以下の問いに答えられる内容だけを仕様書に書く:

```
- このコードが存在する「目的」は何か？
- どのコンポーネントが関わり、それぞれの役割は何か？
- データはどこから来て、どこに行くか？
- この設計で「あえてやらないこと」は何か？
- 次の担当者が知っておくべき制約・注意点は何か？
```

### ステップ 3: 出力ルール

| 状況 | 対応 |
|---|---|
| 既存の仕様書がある | 変更されたセクションのみ差分更新。変更していない箇所は触らない |
| 新規作成 | `x30_仕様書/_templates/spec-template.md` をコピーして使用 |
| 仕様書ファイルが肥大化している | システム単位・機能単位で分割し、MOC（`index.md`）からリンク |

### ステップ 4: MOC を更新する

新しい仕様書ファイルを作成したら、上位の `index.md` にリンクを追記する:

```markdown
<!-- x30_仕様書/<システム>/index.md の該当テーブルに追記 -->
| [[新機能仕様書\|新機能の表示名]] | 一行説明 | YYYY-MM-DD |
```

## x30_仕様書 推奨フォルダ構成

```
x30_仕様書/
  index.md                    ← 全体 MOC（全システム・全仕様書の一覧）
  _templates/
    spec-template.md          ← 新規作成時のテンプレート
  <システム名>/               ← システム・ドメイン単位（例: CORE_01）
    index.md                  ← このシステムの MOC
    <機能名>.md               ← 仕様書本体
    <機能名2>.md
  <システム名2>/
    index.md
    ...
```

### MOC（Map of Content）の原則

- **全体 MOC** (`x30_仕様書/index.md`): 全システムへのリンクと一行説明
- **システム MOC** (`x30_仕様書/<システム>/index.md`): そのシステム内の全仕様書へのリンク
- 1 つの仕様書ノートは複数の MOC からリンク可能（フォルダをまたいだ参照は `[[ノート名]]` で行う）
- 仕様書が増えて MOC が見づらくなったら、サブシステム単位で MOC を分割する

## x30_仕様書 の記述形式（Obsidian）

`x30_仕様書/` 内のファイルは **Obsidian** で参照するため、以下の形式を守ること。

### YAML frontmatter（必須）

ファイル先頭に必ず付与する:

```yaml
---
tags:
  - 仕様書
  - <システム名>        # 例: CORE_XX
aliases:
  - <別名>              # 例: XX連携仕様書
system: <システム名>
updated: YYYY-MM-DD     # 更新日を記入
---
```

### リンク記法

- ノート間リンクは `[[ノート名]]` 形式（Obsidian wiki リンク）を使用
- 外部 URL は通常の Markdown リンク `[テキスト](URL)` を使用

### 改訂履歴

ファイル末尾の `## 改訂履歴` テーブルに今回の変更を 1 行追記し、`updated` frontmatter の日付も更新する。
