# フォルダ構成規約

## 基本方針

各プロジェクトは **設計書リポジトリ** と **コードリポジトリ** の 2 つに分割して管理する。

- 設計書リポジトリ名: `{プロジェクト名}Spec`（例: `fabricSpec`）
- コードリポジトリ名: `{プロジェクト名}`（例: `fabric`）

機能・連携先システム単位でディレクトリ名を **両リポジトリで統一** し、
設計書とコードの対応を追跡しやすくする。

---

## 設計書リポジトリ（`{プロジェクト名}Spec`）

コードリポジトリと**同じディレクトリ構造**を持つ。
各ディレクトリ・ファイルがコードのどこに対応するかを一目で把握できるようにする。

### ディレクトリ構造

```
{プロジェクト名}Spec/
├── 00_アーキテクチャ/              # コードリポジトリに対応しない横断的な設計書
│   ├── システム概要.md              ← 全体構成・技術スタック・認証設計
│   ├── 処理一覧.md                  ← 全プログラム（exp_*/imp_*/vw_*）の一覧・実行順序・依存関係
│   └── データフロー.md              ← 外部システム・Local・DB 間のデータの流れ
├── Admin/                      # ワークスペース・環境管理スクリプトの仕様
├── DB/                         # DBリソース定義書（コードの DB/ と同じ構成）
│   └── {DB名}/
│       └── {スキーマ名}/
│           ├── tables/
│           │   └── {テーブル名}テーブル定義書.md
│           ├── views/
│           │   └── {ビュー名}ビュー定義書.md
│           ├── functions/
│           │   └── {関数名}関数定義書.md
│           └── procedures/
│               └── {プロシージャ名}プロシージャ定義書.md
└── Local/                      # ローカルサーバー処理の仕様
    ├── {機能A}/                # コードの Local/{機能A}/ に対応
    │   ├── テーブル・ファイルレイアウト/   # 入出力ファイル・テーブルのレイアウト定義
    │   └── 処理仕様書/                    # 処理ロジック・フロー仕様
    │       └── {処理名}仕様書.md
    └── {機能B}/                # コードの Local/{機能B}/ に対応
        ├── テーブル・ファイルレイアウト/
        └── 処理仕様書/
```

### 設計書のルール

1. ディレクトリ名・階層をコードリポジトリと**完全に一致**させる
2. ファイル名のプレフィックスをコードのファイル名と一致させる

| 種別 | 命名パターン | 例 |
|---|---|---|
| データ取得処理仕様 | `exp_{対象}_{識別子}仕様書.md` | `exp_members_ag仕様書.md` |
| データ送信処理仕様 | `imp_{対象}_{識別子}仕様書.md` | `imp_members_ag仕様書.md` |
| SQL View 仕様 | `vw_{用途}_{システム}_{内容}仕様書.md` | `vw_連携処理_カオナビ_組織仕様書.md` |
| その他処理仕様 | `{処理名}仕様書.md` | `org_chart_ag仕様書.md` |

## コードリポジトリ（`{プロジェクト名}`）

### ディレクトリ構造

```
{プロジェクト名}/
├── Admin/                      # ワークスペース・環境管理スクリプト
├── DB/                         # クラウドDB上のリソース定義
│   └── {DB名}/
│       └── {スキーマ名}/
│           ├── tables/         # テーブル定義ファイル
│           ├── views/          # ビュー定義ファイル
│           ├── functions/      # 関数定義ファイル
│           └── procedures/     # ストアドプロシージャ定義ファイル
└── Local/                      # ローカルサーバー上で動作するプログラム
    ├── {機能A}/                # 設計書の 01_{機能A}/ に対応
    │   ├── programs/           # 処理スクリプト本体
    │   │   ├── exp_*.{拡張子}  # データ取得処理
    │   │   ├── imp_*.{拡張子}  # データ送信処理
    │   │   └── vw_*.sql        # SQL ビュー定義
    │   └── data/               # 処理の中間・一時ファイル（.gitignore 推奨）
    └── {機能B}/                # 設計書の 02_{機能B}/ に対応
        └── programs/
```

### コードリポジトリのルール

1. ディレクトリ名・階層を設計書リポジトリと**完全に一致**させる
2. ファイル名のプレフィックス（`exp_`, `imp_`, `vw_` 等）を設計書と一致させる
3. 一時ファイル・中間ファイルを格納する `data/` は `.gitignore` に追加する
4. 対応する設計書がある場合、**ファイル冒頭のコメントに設計書パスを記載**する

   ```python
   # 仕様: {プロジェクト名}Spec/Local/{機能A}/処理仕様書/{処理名}仕様書.md
   ```

## 設計書 ↔ コード 対応の記載方法

新しい機能・連携を追加する際は、以下の対応表を各プロジェクトの `CLAUDE.md` に記載する。

```markdown
| 機能 | 設計書 | コード |
|---|---|---|
| {機能A}（データ取得） | `{Spec}/01_{機能A}/{処理種別}/` | `{code}/{機能A}/programs/exp_*.py` |
| {機能A}（データ送信） | `{Spec}/01_{機能A}/{処理種別}/` | `{code}/{機能A}/programs/imp_*.py` |
```
